# 设计 Skill

## 目标

把专业任务的方法设计成 Agent 可以据此执行、检查和完成的 Skill。每个 Skill 或职责独立的内部模块都要讲清四件事：

- 目标：用来做什么，产出什么，达到什么标准才算完成。
- 规则：必须遵循什么、禁止什么、应该检查什么，以及如何落实检查。
- 资源：依靠哪些输入、上下文、契约、模板、外部能力与运行条件。
- 路径：如何利用资源、遵守规则达成目标，检查失败或依据不足时如何处理。

交付可使用的 `SKILL.md` 或模块工作流，以及确有需要的规则、模板、契约和脚本。完成标准是职责明确、依据可靠、四项相互一致、执行路径可走通、关键约束有对应检查、检查结果能够支持完成判断。只解释或审查时直接回复，不未经授权修改文件。

## 规则

### 依据与职责

先从用户目标和该领域的专业理解确定方法，再组织 Skill。已有脚本、模板、目录和历史产物是现状，不能反过来定义专业职责。用户明确要求和项目共同约定优先；发现方法与权威知识冲突时说明并修正对应 Skill，不暗中改写知识来迁就实现。

一个 Skill 可以负责多项相互支撑的工作，但必须明确职责边界、产物归属及与其他 Skill 的协作。内部模块按自身目标具备四项要素，共同规则可以引用唯一来源，不需要重复复制。总入口负责发现与路由，不要求每次执行全部模块或全部阶段。

只修改本次授权的 Skill、必要的关联契约、索引和接入引用，保留已有改动。不因维护 Skill 自动修改下游项目产物、安装依赖、提交、推送或对外回写。局部调整只处理相关范围，不把一个具体项目的机制变成所有任务的固定要求。

### 四项的归属

目标写产物与完成标准；规则写专业判断原则、行为边界、检查要求及执行检查的脚本；资源写完成专业工作所需的材料和能力；路径写动作、检查节点、失败分支与交付条件。

按职责归属组织内容，不能因脚本是可调用工具就把检查脚本主要归入资源。规则先确定应该检查什么，再决定由脚本还是内容审查落实；不围绕现有脚本反向定义检查，也不要求所有检查都脚本化。

模板主要属于资源；规定模板必须表达什么的契约属于规则。外部接口用于完成业务工作时属于资源，用于验证约束时在规则中说明其检查职责。一个载体有多种用途时，明确用途并引用，不重复维护同一事实。

### 约束与检查

规则从目标和专业要求推导，覆盖影响正确性的责任、依赖、状态、边界、兼容与写入范围等实际问题，按任务需要选择，不要求每个 Skill 填写同一套检查字段。

对每项关键约束明确检查对象、判定依据、检查方式及失败后的处理。确定性的检查适合脚本执行；业务含义、方案合理性和未结构化的判断交给内容审查，不能用字段非空证明语义正确。

脚本承担可重复、可验证的检查，说明输入、调用方式、依赖、副作用、退出码及覆盖边界。只读检查不得顺手修复或生成目标项目产物；必要的基线等临时输出明确位置和用途。检查脚本自身的结构化输入要求也要写清，不能悄悄要求产物满足隐藏格式。

格式、内容一致性、最终改动范围与运行行为分别能证明不同结论。按任务选择必要检查，不把“格式通过”“回归通过”或“文档写完”当作整体完成证据。事后范围检查不等于权限隔离，基线应保留用户执行前已有修改；记录不能覆盖的范围，不用扩大允许范围、改写契约或重建基线消除违规。

检查失败后，在职责范围内修正并重查；涉及上游缺口、越界或用户决策时停止依赖它的操作，说明原因和影响。不自动回退用户修改，不反复无界重试。必要检查未执行或无法运行时明确未验证，不能报告闭环完成。

### 内容与维护

四项原则用于组织方法，不能为了章节齐全制造无用产物或机制。保留有效的专业判断、方法与重要约定；精简重复铺垫，不删掉影响正确性的细节。使用稳定标识与明确引用，避免多处复制权威定义。

`SKILL.md` 保持必要入口与核心方法，细节按需放入 `references/`，模板放入 `assets/`，脚本放入 `scripts/`。只有存在具体用途才新增资源目录、模板、检查器或测试，不默认生成测试目录、报告、README 或额外工作流文件。

## 资源

| 资源 | 用途与使用条件 |
|---|---|
| 用户目标、使用场景、期望产物和授权范围 | 确定 Skill 的任务、完成标准与改动范围；现有信息充分时直接设计 |
| 项目共同约定及领域知识、经验和专业方法 | 决定职责与规则；只读取当前目标相关内容 |
| 已有 Skill、模块关系、项目产物和实际失败案例 | 识别现状、调用关系、重复约束和真实缺口；案例不自动成为普遍要求 |
| 已有格式契约、模板、外部接口资料和运行环境说明 | 确定可用输入、表达方式与能力限制，避免设计不可执行的依赖 |
| Skill 所在仓库及其发现入口 | 确定源码位置、目录命名和引用方式；可编辑源码位于独立 Skills 仓库的各 Skill 目录。其他项目执行 `npx @awayercode/skills`，写入 `.agents/skills/`，同名目录覆盖。修改仍回到独立 Skills 仓库。 |

资源说明是否必需、用途、读取或调用位置及缺失影响。用项目相对路径、模块实际位置和可配置参数，避免绑定某台机器。外部能力与当前版本的限制需要时查证权威资料，不预设未经确认的服务或凭据。

## 路径

### 1. 确定目标和当前范围

识别新建、优化还是只读审查，确认期望产物及完成标准。定位共同约定、当前 Skill 和相关专业依据，读取直接相关的模板、契约、脚本及调用者。不默认加载整个仓库或重做整套 Skill。

### 2. 定义规则和检查

从专业要求确定判断原则、职责与行为边界，列出需要检查的关键约束。识别哪些已有检查可复用，哪些需要补充，哪些必须由内容审查完成；资源和脚本不足不能被包装成“检查通过”。

### 3. 明确资源并设计路径

列出必要输入、上下文、已有契约、模板和外部能力，说明获取方式与缺失影响。把执行动作、输入检查、产物检查、改动范围核对、失败修正和交付组织为可执行路径。简单任务保持简洁，复杂任务按依赖分支，不机械要求所有阶段串行。

### 4. 落实到 Skill 与必要支撑文件

按目标、规则、资源、路径组织入口或模块工作流，同步受影响的模板、契约和消费者。新增脚本只承载实际检查或稳定操作，保持检查标准与文档一致。其他项目通过 `npx @awayercode/skills` 获得发布快照并写入 `.agents/skills/`。可编辑源码只保留在独立 Skills 仓库。

### 5. 检查、修正和交付

用实际使用场景核对四项是否一致：目标中的每项产物有完成标准，重要规则有检查方式，路径所需资源能定位，每项必要检查有执行节点和失败处理，产物能够供后续工作使用。

检查引用、元信息、契约与模板一致性、相关消费者兼容和本次改动范围。新增或修改脚本时，使用有实际意义的合法及违规输入验证它会通过什么、拦截什么；按用户要求和项目约定选择是否保留测试文件，不把验证过程自动变成额外产物。

发现问题修正后重查，区分实际验证、内容审查与未验证结论。最终交付 Skill 位置、项目接入、主要规则与检查结果，不以回归数量代替有效性，也不未经授权提交或推送。
