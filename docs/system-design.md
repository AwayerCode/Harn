## 设计依据与范围

### 核心判断

Harn 分为 Agent 层与 Harness 层。Agent 是外部执行主体；Harness 以 Skill 为核心，提供方法、标准与工具。Skill 连接两层，指导 Agent 完成一个独立任务。Harness 内采用 Go CLI + Skill：Skill 承载方法与项目适配，CLI 承担确定性校验，不设置可编程扩展层。

> Skill 定义执行—校验—反馈—修正流程；Agent 执行循环；swe-cli 完成一次确定性校验并返回结果。

首版支持设计、实现、测试与只读审查任务，不要求每次任务经过全部专业工作流。交付目标是有范围、有证据的任务结果；审查任务发现问题也可以正常完成，不能强制审查者修复被审查对象。

本次是目标系统设计，不宣称新能力已经实现。当前仓库有 Markdown 工作流、Python 检查器、Go 分发工具 harn，以及已提交的 Node swe-cli 原型。该原型仅作为迁移参考，尚未改写为 Go；本轮只更新设计，不修改实现。本文及接口协议中的新命令、路径和数据是设计约定，实施前通过契约评审和 Go 构建验证。

### 范围与明确排除

保留现有专业方法、职责分离、权威文档和检查覆盖。补齐单任务的检查清单、统一结果、修正与退出规则，并将稳定检查迁移到 Go 独立可执行文件。项目差异通过 Skill、项目约定、契约及声明式配置表达；项目测试、lint 和构建由 Agent 按 Skill 调用已有工具。

任务队列、依赖调度、多 Agent 派发、后台服务、模型调用和自动自我改进不在本次范围。外层循环保留为整体框架的未来方向，不成为独立任务的前置依赖。任务进度先由会话承载；需要跨会话接续时提供交接摘要，不为此建设数据库或任务管理 CLI。

## 责任分层

### 两层系统边界

Agent 层负责理解目标、执行专业判断、修改授权产物、调用工具并确认整体完成。Harness 不自行调用模型。用户或宿主通过项目约定、明确任务指令或原生 Skill 机制使 Agent 读取 SWE 入口；harn 不自动改写业务项目的 AGENTS.md。

Harness 的中心是 Skill：总入口选择专业方法，共享执行规范承载任务内闭环，专业 workflow 引用它并说明本专业的输入、动作和完成条件。swe-cli 和分发工具围绕该流程服务。

### Harness 内职责与依赖

下表的责任层是内部实现分类，不增加产品层次。Skill 流程在 Agent 会话中运行；单次检查在本地短生命周期进程中运行；harn 仅在安装、检查或更新资源时运行。

CLI 请求入口组合规则计算与文件读取。规则计算不依赖某个 Agent、安装器或具体 Git 实现。harn 与 swe-cli 通过发行协议连接，不相互导入源码。CLI 不加载外部脚本或插件；Skill 引用公开命令而非内部实现。

## 状态与资源所有权

| 状态或资源 | 所有者 | 作用域 | 修改权 | 生命周期 |
|---|---|---|---|---|
| 单任务上下文与轮次 | skill-flow | 当前 Agent 会话，必要时有显式交接摘要 | skill-flow | 开始至交付或退出；由执行该流程的 Agent 维护 |
| 方法与标准资源 | skill-flow | 版本化 SWE 资源 | skill-flow | 仅授权的方法或标准维护任务修改；普通业务任务只读 |
| 单次原始校验结果 | check-entry | 一次调用及其明确输入 | check-entry | 输出后作为该轮证据，不原地改写历史结论 |
| 范围基线 | workspace | 单任务、单 Git 根目录 | workspace | 写入前在项目外创建，后续只读，不能重建消除违规 |
| 配套安装清单与提交状态 | distribution | 单项目的所选资源 | distribution | 安装至移除，受锁保护 |
| 下载缓存与暂存备份 | delivery-io | 一次安装事务 | delivery-io | 成功清理；恢复所需数据保留至恢复完成 |

模块所有权表达职责，不代表工具可以自行扩大权限。任务上下文默认不写文件，Review 仅在回复中返回结果；用户指定持久化时才按其授权保存交接。项目源码、项目自定义方法和配置 与业务契约由项目维护者拥有，安装器和检查器不取得其修改权。

## 关键协作路径

### 安装与进入任务

1. 用户通过 harn 选定 SWE 资源和明确版本。distribution 按 `协议:release.fetch` 取得资源与对应平台二进制，按 `协议:install.commit` 校验并提交配套安装。
2. 用户或项目约定使 Agent 按 `协议:skill.enter` 读取入口。Skill 识别任务类型，选择专业 workflow；没有依据时只阻塞相关动作，不强制补齐全套设计。
3. Agent 确认目标、依据、可写范围、完成条件、必需检查和可用环境，构成任务上下文。专业依据引用项目现有权威位置，不创建第二套要求。

### 可修改任务的闭环

1. Agent 按共享执行规范在写入前建立范围基线；核心经 `协议:workspace.read` 读取工作区，基线保存在项目外全新路径。
2. Agent 执行当前专业任务；核心不生成或修改业务实现。
3. Agent 按 `协议:check.run` 提交本轮请求。check-entry 核验版本和必需项，调用 rules 完成检查并归并结构化结果。
4. Agent 区分业务缺陷、输入问题、环境故障、契约问题与工具缺陷。只修正授权范围内产物；不能修改核心、隐藏诊断或放宽检查来取得通过。需要改变契约或职责时退出并说明决策需求。
5. 修正后增加轮次并重新校验。项目构建、单元和集成测试由 Agent 按专业方法运行，保留其原始证据；CLI 的结构检查不替代这些验证。
6. 必需机器检查通过后，Agent 核对业务完成条件和非机器验收项。只有证据对应最终产物才交付完成；否则继续修正或明确退出。

闭环的运行规则拟落在 execution.md，专业 workflow 只声明适用检查与专业完成条件，不各写循环。无需新建 loop CLI、常驻进程或模型 SDK。

### 退出、只读任务与恢复

目标规则采用默认最多 5 轮、连续 2 轮无进展退出，作为设计建议。当前 execution.md 的“同一问题连续三次无法修正”在实施时由这一统一规则替代，不让两套计数并存。任务开始前可以明确不同上限；不得遇到失败后自行重置轮次。无进展依据是相同问题持续存在且没有有效修改或新证据，不仅比较问题数量。

停止原因包括完成、需要决策、工具或外部阻塞、停滞、轮次或明确预算耗尽、用户停止。返回实际产物、检查证据、未解决问题和恢复条件；退出不自动回滚、提交、推送或发布。次数限制由 Agent 遵循 Skill 执行，CLI 不宣称强制控制跨调用循环。

Review 在开始和结束核对只读指纹，只运行可证明无写入的检查，不创建任务文件、报告或缓存。发现业务缺陷是审查产出，不是要求 Review 修改的失败。若审查自身缺少证据则补充授权内的只读分析或报告限制；需要修复时结束 Review，另行进入获授权的实现职责。

跨会话通过 `协议:task.handoff` 返回最小交接信息。恢复时核对当前产物、版本、原基线和既有证据，旧证据失效就重新检查；基线丢失不能补造原始状态，也不能报告历史范围已验证。首版不自动领取或分发下一任务。

### 迁移与设计验收依据

| 现有能力 | 目标公开能力 | 必须保持的语义 |
|---|---|---|
| validate_documents.py | check 中的 documents 检查项 | 按类型加载唯一 schema，区分格式与语义 |
| check_design.py | design 检查项 | 关系、依赖、所有权和协议一致性 |
| check_artifacts.py | artifacts 检查项 | 已实现的产物检查与未验证边界 |
| check_scope.py | scope snapshot/check/readonly | 原基线、Git 与子模块覆盖、0/1/2 退出码 |
| swe-system-review/check_readonly.py | scope readonly 兼容迁移 | 先确认现有包装行为和参数，不丢失只读证据 |
| swe-system-review/check_structure.py | structure 检查项 | 现有公开入口与结构规则，保留不可检查语义 |

实施顺序：先将现有 Node 原型的文档检查、结果协议和有效测试迁到 Go，移除 Node 打包与 TS 扩展执行机制，再迁移其余 Python 检查和统一输出，随后接入 Skill 闭环，最后接入 harn 配套分发与恢复。逐项用原正反例验证语义，确认迁移后再移除旧 Python 运行路径；运行时不得静默回退 Python。无需在本次全面迁移开发仓测试。

设计对应的交付门槛：一次失败后修正并通过；核心通过但业务条件未满足时不交付；缺失必需检查或工具异常不报成功；Review 无写入且允许带发现交付；停滞和预算退出可解释；无系统 Node/TS/Python/Go 的发行环境可运行核心；损坏恢复同一版本、更新失败不暴露可用的混合版本。接口的可观察承诺见配套协议。迁移必须保留六个脚本的正反例、范围与子模块检查、参数错误及缺失依赖语义；构建产物验收不能仅用源码测试替代。

## 横切基础设施与运行组装

### 单次校验运行

runtime 负责创建读取适配器与规则并注入 check-entry，结束时释放资源。核心默认只读业务项目，结果写 stdout、诊断日志写 stderr；只有明确的 scope snapshot 操作创建项目外基线。输出保存由调用方处理，Review 不保存报告。

配置来源按职责区分：发布清单固定核心与规则兼容关系；Skill 和任务契约确定必需检查；项目配置声明适用检查、规则参数与输入路径；调用参数明确本轮输入。重复或冲突的规则报错，不用通用“后者覆盖前者”让项目配置关闭必需检查。CLI 只能保证提交给它的检查计划完整执行，Agent 是否遗漏应该提交的要求仍须流程验收。

### Go CLI 与 Skill 定制

harn 和 swe-cli 均使用 Go，按平台编译独立可执行文件，不携带 Node 或 TS 执行器。二者职责仍分离：harn 管分发，swe-cli 管单次校验。源码语言相同不意味着合并成一个工具。

Skill 保存共同方法及项目适配指引；项目约定、契约和声明式配置保存技术栈、目录边界、检查参数与验收要求。项目配置与自定义方法独立于托管资源，更新时保留。CLI 只解释已支持的配置，不执行配置中的任意代码，也不提供外部插件接口。

项目已有测试、lint、构建和专属检查由 Agent 按 Skill 调用，证据与 CLI 结果分别保留。Skill 可扩展工作方法，但不能凭文字代替可执行校验；新增稳定的通用检查应回到 swe-cli 源码，经测试与发布交付。业务任务不能为了通过而修改已安装工具或放宽标准。

取消 TS 扩展层同时取消扩展宿主、扩展协议、扩展版本绑定与随包运行时。现有 Node 原型暂留仓库作为迁移依据，后续以 Go 对照验证后移除；原型的通过记录不作为 Go 发行验收证据。

### 分发与完整性

沿用 harn 的 Go 实现、项目本地安装、明确版本和本地修改保护。建议核心位于 `.harness/skills/swe/bin/swe-cli`，Windows 为 `.exe`；它与 Skill 资源配套绑定。二进制目录应加入业务项目忽略规则，Skill 和绑定元数据可入 Git；迁移使用指南时说明该新增忽略项，当前指南仍只描述已实现布局。

发布记录绑定资源修订、核心和接口版本、平台与摘要；新增数据结构需演进现有 downloads.json v1，不能把新增字段当作旧版 harn 自动支持。旧客户端不能处理新记录时明确拒绝。项目配置与自定义方法位于托管资源之外，更新不覆盖它们；托管 Skill 遵循现有本地改动保护。

所有配套产物先下载、验证、暂存，取得项目锁后提交。多文件替换不声称天然原子：提交期间设置不可用标记，swe-cli 遇到标记拒绝启动；成功后才发布新绑定并清标记。失败回滚；崩溃或回滚失败保留恢复信息并拒绝使用混合状态。检查与更新使用相容的读取/写入锁，避免检查过程中切换资源。锁资源由安装器预先建立，检查只获取不会写文件的共享锁；缺失则报告不可检查，不在 Review 中补建。事务和绑定记录遵守 `协议:install.record`。

SHA-256 用于发现误删、损坏和不一致，不承诺对有写权限者的恶意替换安全。二进制主要减少业务 Agent 局部修改检查逻辑的机会；整体仍可被删除或替换。缺失时由 harn 恢复绑定版本，不联网取 latest，不重建第二个安装器。

## 技术选型

| 技术项 | 选择 | 理由与取舍 | 决策状态 |
|---|---|---|---|
