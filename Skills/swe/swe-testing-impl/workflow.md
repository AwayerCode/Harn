# 测试实施

## 目标

独立验收、跨模块及集成测试由本模块维护；模块实现可维护事先明确的本模块单元测试。同一测试文件只指定一个维护责任方，测试预期始终来自契约。

交付对应测试设计的测试代码、隔离数据、替身、配置及可重复入口，说明实际运行、失败归属和证据边界。

完成需同时满足本模块专业标准、实际检查和范围核对；关键缺口影响哪些目标要明确，不以格式通过代替语义或行为正确。

## 规则

遵守[按需加载与职责边界](../references/standards/loading.md)，按当前对象读取共同标准与项目契约；不加载其他专业工作流来完成本职责。

### 文件写入边界（强制）

本 Skill 只做测试 Implementation。只允许新增、修改、删除或移动当前任务范围内的测试代码、测试辅助代码、替身、测试数据、有效快照和必要测试工程配置。所有文档及生产代码只读；不修改业务逻辑、UI、生产接口或运行资源来方便测试。

执行前根据测试设计、系统设计的文件映射和项目约定明确允许写入的目录与文件。测试可位于独立测试目录或源码旁；以具体归属和文件清单为准，不把整个源码目录列为可写。共用依赖清单或 CI 文件只允许修改明确属于本次测试接入的配置项，不能改变生产行为或扩大权限。

运行器产生的缓存、覆盖率数据及临时文件仅允许写入本次已明确的测试运行目录，不生成报告文档，不覆盖目标项目其他文件。执行前核对脚本副作用和清理范围，不能重置生产数据或修改共享环境。交付前核对本次实际改动是否在允许范围，保护用户已有改动，发现越界立即停止并报告。

缺少设计、预期矛盾或发现生产缺陷时停止相关修改并反馈归属，不改文档或生产代码。需要纠正时先结束本环节，再进入对应 Design 或生产代码 Implementation。

### 测试代码

- 断言公开行为、业务结果及副作用，不复制被测算法，不通过扩大生产接口便利测试。
- 按适用范围覆盖空结果、拒绝、未知结果、部分成功、重复操作、中断与迟到结果。
- 对高风险场景断言不得发生的行为，例如重复提交、旧身份写回、覆盖新编辑、重复推进或资源泄漏。
- 异步测试控制时间与完成顺序，避免依赖偶然时序或任意长等待；等待有超时并观察明确条件。
- 替身保留被验证的契约，不把关键确认、事务或恢复语义简化掉。内存替身不能证明数据库竞争和重启恢复。
- 架构检查依据项目设计，包含允许与禁止样例，覆盖实际使用的静态、动态和类型依赖；不只扫描字符串。
- 快照只规范化真正不稳定且非业务关键的字段，不抹去业务 ID、顺序、状态或分值来获得通过。
- 新实现出现回归时先定位原因，不能直接更新基线。基线或测试错误需要独立证据；重构基线修正应在旧实现上核验。

### 写入结果核对

遵守[共同执行规范](../references/standards/execution.md#范围与授权)，使用包内 `scripts/check_scope.py` 固定本次范围并核对实际改动。

### 检查要求与执行

每个当前范围的风险与场景都应对应实际测试入口或说明未实施原因；产品缺陷不能通过修改生产代码或弱化断言消除。

| 检查执行 | 作用与条件 |
|---|---|
| [本模块格式规则](references/document-format.md)与 [validate_documents.py](../scripts/validate_documents.py) | 检查必要输入及本模块设计产物的格式和引用；不证明专业内容或运行行为正确 |
| [check_scope.py](../scripts/check_scope.py) | 核对实际写入范围或只读结果；Python 3 标准库和 Git，属于规则的检查执行，不是业务资源 |
| 内容审查、项目检查与实际验证 | 按下面保留的专业要求和完成标准确认内容与行为；涉及运行先确认工具、环境、权限、输出位置和副作用 |

检查执行、范围覆盖、退出码及失败处理统一遵守[执行规范](../references/standards/execution.md)。


## 资源

| 资源 | 用途与条件 |
|---|---|
| 用户目标、共同约定、任务范围与验收要求 | 决定本轮应交付或审查的内容，不替代专业依据 |

输入按用户路径、项目索引和实际引用定位，只读取当前相关部分。资源不足明确影响；未确认的业务规则不由实现、测试或界面补造。


## 路径

### 执行前范围核对

先确认任务、权威输入和实际可写文件，在首次写入前固定范围：

```bash
python3 -B <SWE目录>/scripts/check_scope.py snapshot --root <目标Git根目录> --baseline <项目外全新临时文件> --allow-file <允许文件相对路径>
```

多个文件重复 `--allow-file`；只有明确职责独立的目录才可用 `--allow-dir`。运行产物也要事先限定；混合源码目录和整个仓库不能当作可写范围。默认只维护自己负责的产物，不因为检查失败修正其他模块产物。

### 执行前文档检查

必需输入：测试设计与当前测试的接入依据。按场景需要读取系统设计、接口协议、业务模型或交互规范；不要求不相关类型齐备。所有输入只读，场景所依赖的语义缺失时停止对应实施。

按用户路径、项目索引和实际引用定位权威文档，读取风险矩阵、场景、预期、替身边界、数据隔离、执行与停止条件。必需输入缺失、格式不合格或不足以定义预期时停止，不根据当前输出反向补造断言。

业务模型及其他文档格式统一由[共同产物规范](../references/standards/artifacts.md)维护。按声明的输入类型使用共享校验器，仅读取相关专业依据，不要求加载生产方工作流。命令使用实际安装路径，条件性文档只在对应范围需要时检查：

```bash
python3 -B <SWE目录>/scripts/validate_documents.py --kind test-design --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind system-design --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interface-protocol --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind business-model --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interaction-standards --file <文档路径>
```

### 工作方法

1. 对照测试设计建立风险、场景、断言与测试入口的映射，按当前任务范围实施，不自选新的业务预期。
2. 复用项目运行器，编写测试和必要替身，落实数据隔离、可控时序、观察与清理。
3. 接入实际执行入口，运行针对性的测试，确认场景能验证设计约束；不靠编译成功、测试数量或覆盖率代替行为证据。
4. 区分生产缺陷、测试实现错误、设计缺口和环境限制；只修复本范围的测试实现错误。
5. 复查失败场景与修改影响。通过后只因新变化、失败或剩余风险扩大验证。

### 执行与完成标准

在允许的隔离测试环境内按设计运行，记录命令、环境、实际结果、覆盖边界和必要清理。未执行或阻塞说明原因，不把历史通过当作当前证据。需要真实持久化或外部链路的场景明确环境与授权，替身结果不能证明真实事务、重启或竞争正确性。

交付测试代码、必要测试配置与可重复入口，结果直接回复，不创建或更新设计和报告文档。说明场景实现情况、生产缺陷、未覆盖范围与阻塞。最终测试审查读取这些已有产物即可，不依赖安装本 Skill。提交与推送遵循用户授权。

### 结束核对与覆盖确认

```bash
python3 -B <SWE目录>/scripts/check_scope.py check --root <原Git根目录> --baseline <原临时基线文件>
```

格式或本模块产物错误在允许范围内修正后，重新执行相关检查和范围核对；内容审查产生新改动时同样重查。上游缺口、越界、生产缺陷或环境阻塞按职责反馈，不以弱化检查取得通过。

每项本轮目标对应产物和检查结果，必要能力未验证时明确限制，不能把“代码或文档已写完”当作已验收。修改范围核对还需人工确认允许文件内的职责与共用配置条目。

收尾前确认结果与实际证据一致，简述检查、未覆盖项和阻塞，不默认生成报告。提交、推送或对外回写遵循用户授权。
