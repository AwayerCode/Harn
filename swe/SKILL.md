# SWE

## 执行主线

先明确当前负责的层或模块、适用标准、接口与质量承诺、可写范围和验收证据，再选择执行能力。系统尚未设计时，按“业务依据 → 分层 → 模块划分 → 标准与契约 → 实现 → 验收”补齐必要依据；已有合格产物直接使用。

本入口只负责发现、选择与协调，专业细节由下表工作流承担。模块是交付对象，Skill 是执行方法，不要求一层对应一个 Skill，也不强制所有项目使用相同层次。

按需加载与边界统一遵守[加载规范](references/standards/loading.md)。以下工作流可直接进入，普通使用无需加载其他专业方法。

## 标准与契约来源

1. [共同工程标准](references/standards/engineering.md)和[实现运行约束](references/standards/implementation.md)定义适用的工程规则；[执行规范](references/standards/execution.md)定义范围、失败处理和证据要求。
2. [产物规范](references/standards/artifacts.md)及 `references/artifact-schemas/` 维护唯一文档格式，模块只声明输入输出类型；共享校验器位于 `scripts/`。
3. 目标项目保存实际业务、系统设计、模块契约、质量指标和验收条件；沿用权威路径，不复制通用方法。项目工程约定记录采用标准、版本和特例，机器契约与文档明确各自权威范围。

执行只加载相关规范、项目契约与专业工作流，不加载制定标准的方法来使用标准，不加载所有层或全部知识。

## 协作与改动范围

设计与实现职责分离：架构设计维护分层与技术章节，模块设计维护模块与协议章节，交互和测试设计维护各自产物。共享文档按章节归属，交付前核对实际改动，文件级范围检查不能证明章节未越界。

实现只修改任务指定模块、必要配置和明确的本模块单元测试；文档、其他层与模块及独立验收测试只读。测试实施维护指定测试与必要测试配置；Review 只读。混合目录细化到文件，共用配置细化到条目，不把全仓或整个源码目录作为默认可写范围。

标准和契约不能由实现者为迁就实现自行改写，验收不放宽预期取得通过。问题回到负责的标准、设计或实现模块；有充分依据的无关工作可以继续。任务按依赖组织，不机械切换所有阶段。

范围检查覆盖 Git 跟踪与非忽略文件、子模块引用、检出版本和可检查文件；未初始化子模块不自动初始化或拉取。父仓库允许范围不能跨入子模块，确需修改时在子模块 Git 根目录独立建立基线。保留用户已有修改，不重建基线掩盖变化，检查不等于权限隔离。具体调用和覆盖边界见执行规范及共享脚本。

格式、结构、语义、行为和集成检查各自提供不同证据。必要依据缺失只阻塞相关操作，未运行或不能检查明确为未验证。验收必须对应实际产物与证据，提交、推送、部署及发布遵循用户授权。
