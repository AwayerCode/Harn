# SWE

## 入口与模块定位

本 Skill 统一组织软件工程工作，内部模块各自保留职责、规则、契约、脚本与模板。根据用户目标和已有产物选择当前模块，读取下表链接的 `workflow.md`，再按该模块指引读取必要资源；不默认加载全部模块，不要求每次从业务建模开始或执行全部阶段。

下文保留各模块原有的 `swe-*` 名称；内部文档中的“本 Skill”指当前模块，“本 Skill 目录”指该模块所在目录，不是 SWE 总目录。其他模块的名称通过本入口定位，不要求它们另行安装或成为独立的发现入口。

各模块的 `references/` 保存规则与契约，`assets/`（如有）保存产物模板，`scripts/validate_documents.py` 执行格式校验。业务模型的规范、契约与校验器统一由 `swe-business-model` 维护，其他模块按需读取或调用；模块之间的相对引用按文件实际位置解析。`scripts/` 保存包内共用的范围及设计对应关系检查，模块在规则中明确引用，在路径中规定执行节点，不复制到目标项目。

## SWE Skill 的关系

软件工作分为设计、实现、测试三个阶段。Review 是各阶段的只读检查能力，不是额外阶段。

| 阶段 | Skill | 职责与产物 |
|---|---|---|
| 设计 | [swe-business-model](swe-business-model/workflow.md) | 明确实体、行为、流程、状态与业务规则，交付业务模型文档 |
| 设计 | [swe-system-design](swe-system-design/workflow.md) | 根据业务模型完成系统结构设计、数据协议设计和技术选型，交付系统设计和接口协议 |
| 设计 | [swe-ui-design](swe-ui-design/workflow.md) | 根据系统设计和接口协议定义页面、视觉、操作与状态反馈，交付交互规范 |
| 设计 | [swe-testing-design](swe-testing-design/workflow.md) | 根据业务、系统、协议及适用的交互规范定义风险、场景与预期，交付测试设计 |
| 实现 | [swe-code-impl](swe-code-impl/workflow.md) | 根据系统设计和接口协议实现业务与技术模块 |
| 实现 | [swe-ui-impl](swe-ui-impl/workflow.md) | 根据交互规范、系统设计和接口协议实现 UI、展示资源与界面接入 |
| 测试 | [swe-testing-impl](swe-testing-impl/workflow.md) | 根据测试设计及相关系统、协议依据编写、接入并运行测试 |

设计通过文档衔接后续工作，代码、UI 和测试分别由对应 Skill 实施。测试设计可以在实现之前完成，不根据代码当前输出倒推预期。

| Review Skill | 检查依据与重点 |
|---|---|
| [swe-system-review](swe-system-review/workflow.md) | 对照系统设计检查目录、文件归属、公开入口与文件依赖 |
| [swe-code-review](swe-code-review/workflow.md) | 依据代码、调用路径及适用规则检查逻辑、状态、异常和边界；涉及设计或业务承诺时补充对应文档，缺口只阻塞依赖它的检查 |
| [swe-ui-review](swe-ui-review/workflow.md) | 对照交互规范检查界面、操作路径、视觉、状态反馈及平台表现 |
| [swe-testing-review](swe-testing-review/workflow.md) | 对照测试设计及相关依据检查覆盖、断言、替身和执行证据 |

## 怎么使用

按当前工作选择 Skill，不必每次从头执行所有阶段：

- 业务规则不明确，使用 `swe-business-model`。
- 系统分层、模块责任、数据协议或技术选型需要设计，使用 `swe-system-design`。
- 页面、操作或视觉规范需要设计，使用 `swe-ui-design`。
- 测试场景、预期或验证方法需要设计，使用 `swe-testing-design`。
- 设计已有且合格，分别使用 `swe-code-impl`、`swe-ui-impl` 或 `swe-testing-impl` 实施。
- 只检查现有产物，按对象使用对应 Review。

每个 Skill 执行前自行定位目标项目的权威文档，使用相应负责 Skill 的校验器检查业务模型格式，其他文档使用自身校验器，并确认内容足以支持当前任务。必需依据缺失、格式不合格或规则冲突时停止相关工作并反馈，不自动补建上游设计。首次创建本 Skill 负责的设计文档，无需该产物预先存在。

发现问题后回到对应职责：设计缺口交给相应 Design，业务代码缺陷交给 Code Impl，UI 缺陷交给 UI Impl，测试代码问题交给 Testing Impl。先结束当前环节，再进入下一 Skill；不在当前 Skill 中顺手修改其他职责的产物。

## 改动范围

| Skill 类型 | 允许修改 | 只读范围 |
|---|---|---|
| Design，包括业务建模 | 自己负责的设计文档 | 其他设计、全部代码、测试及工程配置 |
| Code Impl | 业务与技术模块代码、对应资源和必要工程配置 | 全部文档、UI 文件、测试文件 |
| UI Impl | 页面、组件、样式、展示资源和必要界面配置 | 全部文档、业务与技术模块代码、测试文件 |
| Testing Impl | 测试代码、数据、替身和必要测试配置 | 全部文档、生产代码 |
| Review | 无 | 所有文件 |

这些边界最终对应目标项目的目录与文件。设计通常在 `design/`，代码与 UI 位于系统设计指定的源码目录，测试位于项目约定的测试目录；具体路径沿用项目实际结构，不要求统一搬迁。Monorepo 同样按应用与包确定范围。

执行前根据项目约定和系统设计确认本次可写路径；混合目录及共用配置细化到文件或配置项，不把整个仓库或整个源码目录作为通用可写范围。项目只需补充自身路径和必要例外，职责规则不变。执行后核对本次实际改动，保留用户已有修改。

范围与只读检查遇到 Git 子模块时，不跳过也不直接报错：记录父仓库的子模块引用和实际检出版本，递归核对已初始化子模块的 Git 跟踪及非忽略文件；未初始化子模块记录引用及未初始化状态，并核对其中现有普通文件，不自动初始化或拉取。子模块中的忽略文件与 Git 内部文件仍不在覆盖范围，检查不提供权限隔离。

父仓库的可写范围不得跨入或包含子模块；确需修改时，以该子模块的 Git 根目录单独建立基线，再依相应模块执行。父仓库检查仍能发现子模块版本或文件变化，不因子模块与本轮任务无关就漏查。系统设计的 `check_changes.py` 和系统结构审查的 `check_readonly.py` 复用包内 `scripts/check_scope.py` 的文件核对逻辑，随 SWE 包保留该依赖。

共享范围检查中的每条 Git 命令最多等待 10 秒；超时、仓库损坏、目录或文件无法读取时，明确报告对象与原因，按“无法检查”处理，不能忽略后声称通过。10 秒是单条命令限制，不是整个文件扫描的总时限。共享脚本缺失时明确提示完整包依赖；不自动拉取、修复仓库或扩展可写范围。

边界包括新增、修改、删除、移动以及工具产生的文件。Review 不修复、不生成缓存或报告；无法无写入地运行验证时说明未执行，实际运行交给对应实施环节。结果直接回复，不额外生成实现、测试或验收报告。格式校验不代替语义审查与行为验证，也不提供文件系统权限隔离。提交、推送及外部回写遵循用户授权。
