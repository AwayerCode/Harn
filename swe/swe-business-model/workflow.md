# 业务建模

## 目标

交付唯一权威业务模型，以业务实体、业务行为、业务流程表达已明确的业务；核心价值可解释、抽象与职责成立，未确认事项不写成事实。

完成需同时满足本模块专业标准、实际检查和范围核对；关键缺口影响哪些目标要明确，不以格式通过代替语义或行为正确。

## 规则

遵守[按需加载与职责边界](../references/standards/loading.md)，按当前对象读取共同标准与项目契约；不加载其他专业工作流来完成本职责。

### 工作范围

只新增或修改业务模型文档。其他设计、源码、测试、工程配置和资源只读，不顺带补建系统设计或实施代码。沿用项目位置；首次建模未指定位置时，默认使用 `design/business-model/business-model.md`。执行前确认具体可写文件，保留用户已有修改。

### 职责与判定要求

现有文档、页面、文件名和表结构是业务证据，不直接给出实体。模型只写已明确的业务定义。建模建议、假设和未确定问题在对话中讨论，不写入模型或另建问题清单文件；不创造账号、权限、组织、数据政策或产品范围。影响当前建模的关键问题先向用户提出，明确后再写入；同时继续不依赖答案的部分。


### 三层建模

阅读[抽象方法](references/modeling-principles.md)。先理解软件承担的核心业务价值，解释领域概念，再按以下三层建立模型；从中识别最小稳定核心，判断扩展能力如何围绕核心组合生长。这是思考主线，不要求增加文档章节，也不要求局部修改重新建立完整模型。

对象间的使用、包含、归属等含义写在实体定义及其行为中，不另建“实体关系”层或章节。功能是业务行为在特定交互入口上的表现，不作为模型的稳定边界。

#### 业务实体

透过具体用途和产物名称，找到共同本质的业务对象。定义实体是什么、承载什么内容；角色、类型、属性和表现形式归入相应实体。

不得把每个业务名词、流程输出或文件都直接建成实体。实体应能够在业务中独立存在并持续变化；能编号、能单独区分不足以证明独立性。用独立业务含义、持续身份与行为职责判断是否需要拆分；仅换一个更概括的名字不算抽象。也不要为减少数量把有不同职责的对象塞进万能的“内容”或“资源”。

教育场景中的用户、素材、课程是抽象方式的示例，不是必须照搬的实体名单。具体对象是否成立由业务决定，不预设课程平台、题库或考试功能。

#### 业务行为

按实体组织其行为，说明对象能做什么或接受什么业务处理。需要时写出执行者、业务依据、作用内容、结果及约束，不强制填写固定表格。

一个行为涉及多个实体时，按职责归属描述，不重复造多个行为。用户操作与对象接受处理均可表达为业务行为，不据此规定代码方法或技术模块。

行为结果可以是对象形成、内容改变、组织调整或判断确认，不自动产生新实体。说明结果改变了什么业务事实或状态，以及由哪个实体承载。规则与必要状态写在所属实体或行为处。

#### 业务流程

由实体的行为组成实际业务顺序，说明起点、推进条件与完成结果。每一步应能对应前述行为；不能只有输入输出箭头而没有对象与行为依据。

相互独立的工作分别表达，不制造强制顺序；不将流程步骤直接升级成实体。未明确的输入、依据、审阅或完成标准在对话中澄清，不写入流程。可选分支只有在业务含义和适用条件已明确时才纳入，不用条件句包装未确认能力。

### 稳定核心与组合扩展

识别创造核心价值所必需的实体、行为和必要流程。用移除某项能力后核心价值能否成立来检验必要性；核心追求业务意义稳定，不以实体数量最少为目标。

新增能力时先判断它如何使用、组合或补充已有核心，避免每增加一个功能就重定义核心实体。领域事实确实改变核心时可以调整，但需说明依据及对既有实体、行为和流程的影响。核心与扩展的区别写在相关定义中，不增加第四层或强制章节。

### 规则展开与停止

先建立业务结构，再深化影响结构正确性的规则。判断当前细节是否改变实体的意义、关系、行为结果或流程成立条件：会改变时继续说明；只涉及函数调用、算法、数据库操作或技术重试实现时，留给系统设计或代码实现。

业务上的先后规则仍属于模型，例如“付款后才能发货”；实现这一规则的调用顺序与事务方案属于下游。权限、状态、失败与恢复也按业务影响判断，不因属于逻辑就排除，不因存在实现可能就全量展开。

已明确范围的业务结构清楚、核心价值可解释即可交付。存在影响当前结论的缺口时，在对话中指出并澄清，继续不依赖它的部分；模型不收录讨论事项，不靠假设补全规则，也不将局部明确的模型宣称为完整或可直接实施。

### 模型文档

阅读[文档规则](references/document-format.md)，按[模板](assets/business-model.md)组织内容。正文只有“业务实体、业务行为、业务流程”三个二级章节，内部按实体或流程展开。

一级标题后直接进入业务实体。不加入重写依据、历史、工作计划、需求依据、独立实体关系、建模方法或自检结论。

同一业务范围默认只维护一份权威业务模型，沿用已有文件。建模方法、规范与模板由本 Skill 维护，不复制到目标项目；不默认新增优化方案、建模思路、审查报告或历史版本文件。具体产物边界与用户明确要求另存时的处理，见文档规则。

用户只要求审查或提出优化方案时，直接回复，不修改模型。用户要求更新模型时，将已明确且获授权的业务结论整合进现有三层正文，不纳入建议、假设或未确定问题；不能以新方案文件替代更新，却将旧模型留作另一套业务依据。“记录一下”不自动表示另建文件：按内容归属及授权范围更新已有产物；尚未授权修改模型的建议留在回复中，不为保存建议默认建立并行文档。

确认状态由项目已有的状态入口记录；未授权修改该入口时在回复中说明。未明确的业务问题只在对话中提出。清理旧模型时删除未确认内容，不能只去掉“待确定”字样而把假设改写成定义；保留已有明确规则。

### 写入结果核对

遵守[共同执行规范](../references/standards/execution.md#范围与授权)，使用包内 `scripts/check_scope.py` 固定本次范围并核对实际改动。

### 检查要求与执行

已明确问题只整合进业务模型；未确认内容留在对话中，不因模板制造实体或流程。

| 检查执行 | 作用与条件 |
|---|---|
| [本模块格式规则](references/document-format.md)与 [validate_documents.py](scripts/validate_documents.py) | 检查必要输入及本模块设计产物的格式和引用；不证明专业内容或运行行为正确 |
| [check_scope.py](../scripts/check_scope.py) | 核对实际写入范围或只读结果；Python 3 标准库和 Git，属于规则的检查执行，不是业务资源 |
| 内容审查、项目检查与实际验证 | 按下面保留的专业要求和完成标准确认内容与行为；涉及运行先确认工具、环境、权限、输出位置和副作用 |

检查执行、范围覆盖、退出码及失败处理统一遵守[执行规范](../references/standards/execution.md)。


## 资源

| 资源 | 用途与条件 |
|---|---|
| 用户目标、共同约定、任务范围与验收要求 | 决定本轮应交付或审查的内容，不替代专业依据 |
| 用户目标、已确认业务规则、相关业务证据和现有模型；首次建模无需已有模型 | 按下方输入规则定位权威位置和条件性依据，缺少关键内容时停止依赖它的操作 |
| 已有项目工具、环境及历史证据 | 按当前风险选择实际检查；历史通过不代表当前通过，副作用或环境不明时先核实 |
| 本模块 `assets/` 中的模板 | 组织自己的产物，不扩大职责，不按模板虚构业务或能力 |

输入按用户路径、项目索引和实际引用定位，只读取当前相关部分。资源不足明确影响；未确认的业务规则不由实现、测试或界面补造。

### 输入与现状

读取用户目标、具体任务、已确认规则及必要现状。首次建模不要求已有模型。修改已有模型时先读懂其内容；旧格式不合格不能阻止用户明确要求的模型重构。格式通过也不能使旧实体划分成为权威。

## 路径

### 执行前范围核对

先确认任务、权威输入和实际可写文件，在首次写入前固定范围：

```bash
python3 -B <SWE目录>/scripts/check_scope.py snapshot --root <目标Git根目录> --baseline <项目外全新临时文件> --allow-file <允许文件相对路径>
```

多个文件重复 `--allow-file`；只有明确职责独立的目录才可用 `--allow-dir`。运行产物也要事先限定；混合源码目录和整个仓库不能当作可写范围。默认只维护自己负责的产物，不因为检查失败修正其他模块产物。

### 内容检查与格式校验

先从具体场景检查抽象：模型能否解释真实业务；改变用途或文件形式是否仍能使用原实体；实体是否能独立存在且有自己的职责；行为是否归属实体并说明业务变化；流程是否由已有行为构成且确需持续推进；统一是否抹掉真实业务区别。

再检查是否按功能或页面划边界、核心是否足以创造核心价值、扩展是否围绕核心组合，以及是否混入实现细节或遗漏影响业务正确性的规则。自检直接用于修正模型，不额外生成报告或章节。

[格式契约](references/artifact-contract.json)只检查三层文档结构和基本 Markdown，不判断实体抽象是否成立。旧四层或附带说明的文档会报错；下游 Skill 应按业务模型重构处理，不能为绕过校验保留旧格式。

```bash
python3 -B <本 Skill 目录>/scripts/validate_documents.py --kind business-model --file <业务模型路径>
```

其他 Skill 通过共同 schema 与共享校验器读取格式要求，不复制契约或校验逻辑。检查工具不得写入目标项目，Python 使用 `-B` 避免缓存。

交付前检查实际改动范围，并确认同一业务范围没有因本次工作新增并行业务依据或复制建模方法。发现既有重复文件时，不擅自删除、移动或覆盖，先指出职责冲突；用户授权整理后合并独有的有效业务内容，再移除冗余并修正引用。简述实体抽象、内容检查、实际校验结果与未确定问题。格式通过不代表需求已确认、用户已验收或模型足以直接实施。

### 结束核对与覆盖确认

```bash
python3 -B <SWE目录>/scripts/check_scope.py check --root <原Git根目录> --baseline <原临时基线文件>
```

格式或本模块产物错误在允许范围内修正后，重新执行相关检查和范围核对；内容审查产生新改动时同样重查。上游缺口、越界、生产缺陷或环境阻塞按职责反馈，不以弱化检查取得通过。

每项本轮目标对应产物和检查结果，必要能力未验证时明确限制，不能把“代码或文档已写完”当作已验收。修改范围核对还需人工确认允许文件内的职责与共用配置条目。

收尾前确认结果与实际证据一致，简述检查、未覆盖项和阻塞，不默认生成报告。提交、推送或对外回写遵循用户授权。
