# 业务模型文档规则

## 产物边界

同一业务范围默认只有一份权威业务模型，沿用项目已有位置；首次建模未指定位置时使用 `design/business-model/business-model.md`。多个应用或业务域可以分别维护模型，但不得用原模型、优化方案和新模型表达同一范围的并行结论。

正式模型只承载已明确的实体、行为、流程和业务规则；建议、假设及未确定问题在对话中讨论，不写入模型，也不另建问题清单文件。项目已有状态入口承载范围与确认状态，修改仍需符合授权及职责边界；不能依靠状态入口解释新旧两套模型并存。历史变化优先使用已有版本管理，不默认另存旧版或变更说明。

建模方法、规则、契约和模板留在 Skill 中，不作为目标项目的业务模型附件复制。审查结论与优化建议默认直接回复；更新模型时将已授权结论整合进现有正文，不新增长期优化方案或审查报告文件。

只有用户明确要求独立文件、指定另存位置或项目已有明确的独立产物约定时，才另行交付。另存文档的职责及其与权威模型的关系必须清楚，不把建议稿作为第二份当前模型；用户明确指定的组织方式优先，不借本规则扩大修改授权。

已有重复文件不自动清理。授权整理后，应先保留独有的有效业务内容，合并到对应产物，再移除冗余并修正引用，不把方法、历史或审查结论塞入模型正文。

## 三层结构

文档只有一个一级标题“业务模型”。其后直接进入正文，二级章节必须且只能依次为：

1. 业务实体
2. 业务行为
3. 业务流程

三个章节均有实际内容，不重复、不增加其他二级章节。实体定义在“业务实体”中按实体展开；行为在“业务行为”中按实体归属展开；流程在“业务流程”中按具体业务展开。三级及以下标题按需要使用。

不加入重写依据、需求依据、实体关系、建模方法、文档信息、自检结论或独立的待确认清单。对象间的联系写入实体及行为；未明确的规则先在对话中澄清，明确后再写入。状态与规则按业务需要嵌入相应位置，不另建层次。

优先使用短段落，每段表达一个重点。并列信息用列表，具有共同维度的信息优先用表格，有先后顺序的流程用有序步骤。表达形式按内容选择，不强制套版，不把长段落塞进表格，也不因调整排版删减业务信息。不固定表格列名或强制生命周期、状态、权限等栏目，不得为填表创造规则。

核心价值的承担、最小稳定核心及扩展能力的组合关系融入相关实体、行为和流程的说明，不新增二级章节，不要求所有模型使用固定标签。局部更新只展开受影响内容。写清影响业务结构与结果的规则，不写函数、算法、存储与技术调用细节。

模型确认状态和产品范围沿用项目已有状态入口，未授权修改时在回复中交代。用户明确指定不同组织时以用户要求为准，说明本契约的适用范围，不增加用户不要的章节。

## 基本 Markdown

标题不跳级，前后有空行，文件末尾恰好一个换行。不保留模板占位符。代码围栏声明语言且关闭。本地文件与章节引用必须存在，外部链接不做网络验证。

## 校验与内容判断

使用本 Skill 的 `scripts/validate_documents.py`，仅依赖 Python 标准库。退出码 0 为格式通过，1 为格式违规，2 为调用或读取失败。使用 `-B` 避免缓存。

格式契约不再接受旧的四层及附带说明结构。重构旧业务模型时可以读取其内容，不能因为旧格式校验失败而拒绝用户授权的修订。

格式通过只能证明基本结构，不能证明实体完成抽象、行为归属合理、流程成立或需求已确认。按抽象方法进行内容检查后再交付，不额外生成校验报告文件。

内容检查还需确认：核心实体、行为和必要流程能创造所需核心价值，扩展组合有依据，业务规则与实现细节的边界清楚。这些是语义判断，不增加格式门禁。
