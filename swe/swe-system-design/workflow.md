# 系统设计

## 目标

以业务模型为依据完成三件事：系统结构设计、数据协议设计和技术选型。主线是“业务模型 → 系统结构与数据协议 → 技术实现选择”；三者相互校核，关键技术可提前核实，不能以框架、文件或已有依赖反推业务概念。

交付两份相互引用的文档：

- `system-design`：系统设计，记录责任分层、模块与依赖、状态归属、关键路径、运行组装、代码映射及技术选型。
- `interface-protocol`：接口协议，记录模块、外部能力和持久化边界的数据语义、状态变化、失败责任、交互约束及演进规则。沿用文件名称和类型，不将其范围缩成调用接口。

完成条件：当前范围的业务行为与状态有明确责任，跨边界协作有完整承诺，技术能够实现这些承诺；输入、格式、跨文档一致性和写入范围检查均实际运行并通过，内容审查无阻断缺口。未验证项和建议明确列出，不能将草案或阻塞产物报告成已完成设计。

## 规则

### 职责与写入边界

只新增或修改已确认的两份设计文档。默认位置为 `design/system-design/system-design.md` 与 `design/interface-protocol/interface-protocol.md`；已有项目沿用权威位置。执行前列出准确文件，不扩大到整个目录；保留用户已有修改。

业务模型、其他设计、源码、UI、测试、依赖、配置和资源只读。业务含义由业务模型定义，页面与操作细节归 UI Design，算法归 Implementation，测试计划和代码归相应 Testing 模块。不得借设计或检查顺手修改这些产物。提交、推送和外部回写遵循用户授权。

局部任务只调整受影响内容并检查相关协作，不强制重做整套系统。不为模板预设状态机、持久任务、审批、进程隔离或恢复机制；已有数据、状态和跨边界行为必须有明确归属与语义。

缺少必需业务依据、关键规则不明或来源冲突时，停止依赖它的设计并报告缺口，不编造业务模型。用户决策、设计建议和待确认严格区分，旧演示、依赖或模板不自动成为批准方案。

### 系统结构设计

#### 从业务模型确定责任

识别当前范围内独立存在和由其他概念组合而成的业务概念、行为、状态与生命周期。业务规则和状态归属沿用业务模型；业务依据不足时反馈缺口，不借模块拆分重新定义业务。

能够独立存在的业务概念划为不同模块；同一业务概念的内部复杂度由内部组件处理，不根据代码量、文件数量或框架划分业务模块。每项业务行为有负责模块，每份业务状态有明确所有者和修改权。

#### 分层与依赖

按责任区分交互层、业务编排层、业务能力层与技术实现层：交互层接收操作和展示状态；业务编排层组织完整流程；业务能力层提供独立、稳定的业务能力；技术实现层支撑业务运行。按当前范围表达相关层次，不预建无业务依据的空层或模块。

层级表达业务责任与运行时协作，不等于代码依赖方向。平级正交业务模块保持独立，需要组合多项能力时由更高层编排；出现直接业务依赖时重新检查概念组合关系和层级。业务模块通过抽象边界使用技术能力，不直接依赖具体技术实现。

横切基础设施只提供通用非业务能力，不参与业务决策、不拥有业务状态，替换后不改变业务结果。运行组装负责创建、连接、初始化和关闭系统对象，把具体技术实现连接到抽象边界，不承载业务逻辑。

#### 模块与落地

说明模块所属责任层、业务职责、公开能力、允许的代码依赖和能力来源。根据成本、风险和控制权决定复用、采购或自研，明确内外部责任边界；供应方承担什么，以及自身仍承担哪些集成、验证、故障处理和替换责任。

明确状态或资源的所有者、作用域、修改权和生命周期；纯计算模块可以明确无持有状态。沿关键业务路径说明编排者、参与模块和协议引用，不能只列模块清单。将已确定的模块边界、公开入口和依赖约束映射到项目目录或包；首次设计可给出计划位置，不展开无关文件树和脚手架。

### 数据协议设计

数据协议是独立责任边界之间对业务数据及其状态变化的稳定承诺。覆盖当前范围内的模块、用户入口、外部服务和持久化边界；函数、事件、消息、API、文件和数据库只是载体。

先确定每份数据的业务含义、标识、关系、合法状态、不变量及唯一权威来源，再定义边界操作、事件、输入、输出和状态变化。已有机器契约引用准确来源，不另造冲突字段；公共数据统一定义或引用，不能要求消费者理解提供方内部结构。

每项协议明确：

- 数据语义与前置条件：哪些数据有效，操作成立需要满足什么。
- 状态变化与副作用：由谁修改什么，结果何时成立、如何观察；查询或纯计算明确无状态修改。
- 失败语义：错误、部分失败、结果未知时的责任及后续处理；业务需要恢复时说明保留什么、由谁保留、如何恢复。
- 交互约束：按行为明确顺序、幂等、事务、一致性、并发和时序要求，不把这些决定留给实现随意选择。
- 演进规则：说明兼容、版本、迁移和废弃责任；持久化数据尤其要明确跨版本读取与变更关系。

每项协议评估这些维度。无关维度可说明不适用及原因，简单语义可直接说明，不强制引入事务、重试或版本机制。异步或外部调用按真实能力说明完成、超时、取消、重复请求和结果未知。数据结构本身不能代替协议。

为重要边界承诺注明可验证条件或证据来源，供后续测试设计使用，不在此编写测试计划、用例或测试代码。

### 技术选型

从业务能力、系统结构、数据协议和交付运行约束选择技术。只比较影响当前决策的备选方案，记录选择、理由、主要取舍和决策状态；区分用户已确认、设计建议与待确认。已有明确选择直接沿用，变更说明原因。

产品形态、运行环境、语言与框架、存储、模型或外部能力按实际需要讨论，不要求逐项选齐。模块能力来源属于结构与责任边界的判断，技术选型进一步选择具体实现。外部能力通过抽象边界接入，同时核实供应方限制是否满足协议承诺。

涉及当前版本、平台支持或外部能力的判断，查证对应官方资料；区分已验证事实和未验证假设。不通过安装依赖、创建应用或运行演示代替选型说明。

### 可检查的表达与检查边界

跨文档表格采用稳定标识及明确引用，具体规则见[检查表达约定](references/document-format.md#脚本检查的表达约定)。旧格式仍可读取，但缺少结构化依据时不能宣称一致性检查通过；只在本次允许范围内补齐，范围外缺口报告阻塞或未验证。

检查从上述专业规则和写入边界出发：确认输入及产物表达完整、责任与依赖明确、跨边界承诺一致、本次实际改动在授权范围内。能确定性判断的部分由以下脚本执行，业务概念与方案合理性由内容审查判断。

| 检查执行 | 负责落实的检查与运行条件 |
|---|---|
| [业务模型规范](../swe-business-model/references/document-format.md)及其校验器 | 检查上游表达是否符合业务模型契约；缺少对应模块时停止依赖此输入的工作 |
| [格式规则](references/document-format.md)、[机器契约](references/artifact-contract.json)与 [validate_documents.py](scripts/validate_documents.py) | 检查文档章节、字段、占位符和引用，Python 3 标准库，只读 |
| [check_design.py](scripts/check_design.py) | 检查模块、状态归属、显式依赖、协议与路径引用的一致性，同时执行两份文档的格式校验，Python 3 标准库，只读 |
| [check_changes.py](scripts/check_changes.py) | 检查最终改动是否越出固定文件清单；需要 Git，写入前将基线保存在项目外临时文件 |

所有 Python 命令使用 `-B`，按模块实际位置调用。路径规定检查执行的节点；必要检查缺失、失败或无法运行均不能当作通过。上述脚本不判断业务概念正确性，也不扫描源码或验证运行行为，内容审查必须另行完成。

范围脚本复用 [SWE 共享检查](../scripts/check_scope.py)，随包保留该依赖；子模块处理遵守 [SWE 改动范围](../SKILL.md#改动范围)。基线覆盖 Git 跟踪及非忽略文件，也记录子模块引用、检出版本及其可检查文件，不覆盖 `.git`、被忽略文件、项目外文件或执行中修改后恢复的动作。它是事后检查，不是权限隔离；不得修改这些未覆盖对象。不能以脚本通过替代实际范围核对，不能修改、重建基线或扩大允许文件来消除报错。

## 路径

### 1. 定位依据和执行范围

确认当前目标、权威业务模型、配套设计及两份可写文件。检查上游格式并审查相关语义；修改任务先校验已有设计格式，记录需要修正的问题。首次设计无需先校验不存在的产物。

```bash
python3 -B <业务建模模块>/scripts/validate_documents.py --kind business-model --file <业务模型路径>
python3 -B <本模块>/scripts/validate_documents.py --kind system-design --file <已有系统设计路径>
python3 -B <本模块>/scripts/validate_documents.py --kind interface-protocol --file <已有接口协议路径>
```

输入或权威来源的阻断问题先反馈负责模块；本模块产物自身的问题在本次设计范围内修正。无关缺口不阻止其他已明确部分，但应明确局部完成范围。

### 2. 在写入前记录基线

使用目标项目 Git 根目录和项目外的全新临时基线文件，固定两份允许文档，不能用 HEAD 差异代替基线；用户可能已经有未提交修改。

```bash
python3 -B <本模块>/scripts/check_changes.py snapshot --root <目标项目Git根目录> --baseline <项目外全新临时基线文件> --allow <系统设计相对路径> --allow <接口协议相对路径>
```

脚本拒绝覆盖已有基线。若目标项目不是 Git 仓库或基线无法记录，停止写入并说明范围检查无法建立。检查工具只允许基线这项项目外临时输出，不生成项目内报告、缓存或测试产物。

### 3. 完成三项设计

按照上述设计规则，从业务概念形成责任分层和模块边界，确定状态归属与关键路径；将协作落实为数据协议，选择满足承诺的技术，核对三项相互一致。局部任务沿受影响路径检查两份产物，不顺手改业务模型或实现。

### 4. 执行基本检查并修正

```bash
python3 -B <本模块>/scripts/check_design.py --system-design <系统设计路径> --interface-protocol <接口协议路径>
python3 -B <本模块>/scripts/check_changes.py check --root <目标项目Git根目录> --baseline <原临时基线文件>
```

两项检查都要运行并检查退出码：0 为检查通过，1 为发现违规，2 为无法完成检查。后两种均不能视为通过。

一致性或格式错误在两份允许文档内修正，然后重跑两项检查。写入越界时立即停止，不自动回退用户修改，不重建基线；说明具体文件与原因，由用户授权后再处理。相同问题连续三次未解决，停止反复修改，报告阻断项及所需决策。没有实际运行或无法检查时明确标为未验证，不能宣称闭环完成。

### 5. 内容审查、复查和交付

沿真实业务路径核对：行为与状态有责任、分层与依赖符合规则、输入可取得、输出可供下一步使用、必要失败与并发语义明确、技术能兑现协议。检查业务要求但设计遗漏的异常责任，不能只检查设计主动承诺的能力。逐项审查“不适用”理由与未解决问题。

内容审查产生修改时，重跑基本检查和范围检查。完成后直接回复设计决策、实际检查结果、内容审查结论和未验证范围；不另生成实现、测试或验收报告。重要边界承诺的验证依据交给后续测试设计，当前阶段不宣称运行行为经过验证。
