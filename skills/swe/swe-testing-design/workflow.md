# 测试设计

## 目标

交付测试设计，将重要风险落实为场景、输入、预期、禁止副作用、执行层级、替身边界和判定条件。

完成需同时满足本模块专业标准、实际检查和范围核对；关键缺口影响哪些目标要明确，不以格式通过代替语义或行为正确。

## 规则

遵守[按需加载与职责边界](../references/standards/loading.md)，按当前对象读取共同标准与项目契约；不加载其他专业工作流来完成本职责。

### 文件写入边界（强制）

本 Skill 只做 Design，只能新增或修改本 Skill 所负责的设计文档；不能修改任何源码、测试代码、样式、配置、依赖清单、资源或生成产物，也不能顺带更新其他类型的设计文档。

执行前根据用户路径、项目约定和权威文档确认允许写入的准确文件清单。新项目默认位置：`design/test-design/test-design.md`。已有项目使用已确认的设计目录及权威文件位置；不靠扩展名判断，不扩大到整个仓库或所有 Markdown 文档，路径归属有歧义时停止相关写入。

只读参考其他文档与代码。检查工具不能修改代码、配置或生成文件；Python 校验使用 `-B`，避免缓存写入。交付前核对本次实际改动均属于上述清单，区分用户已有改动，发现越界立即停止并报告，不回退用户改动。

需要改代码时在回复中说明实施要求，结束 Design 后由 Implementation 执行；需要改其他设计时交给对应 Design，本 Skill 不跨职责补建或修订。

### 职责与判定要求

把业务和设计约束转化为可实施的测试设计。唯一文件产物是测试设计文档。场景、断言要求、执行入口约定与清理方法写入设计；测试代码和工程接入交给 swe-testing-impl。

### 写入结果核对

遵守[共同执行规范](../references/standards/execution.md#范围与授权)，使用包内 `scripts/check_scope.py` 固定本次范围并核对实际改动。

### 检查要求与执行

预期来自业务与设计，不能从当前实现输出倒推正确答案；场景覆盖与未覆盖风险都要明确。

| 检查执行 | 作用与条件 |
|---|---|
| [本模块格式规则](references/document-format.md)与 [validate_documents.py](../scripts/validate_documents.py) | 检查必要输入及本模块设计产物的格式和引用；不证明专业内容或运行行为正确 |
| [check_scope.py](../scripts/check_scope.py) | 核对实际写入范围或只读结果；Python 3 标准库和 Git，属于规则的检查执行，不是业务资源 |
| [check_artifacts.py](../scripts/check_artifacts.py) | 根据本模块产物检查显式对应关系；用法及未覆盖语义见下文，Python 3 标准库，只读 |
| 内容审查、项目检查与实际验证 | 按下面保留的专业要求和完成标准确认内容与行为；涉及运行先确认工具、环境、权限、输出位置和副作用 |

检查执行、范围覆盖、退出码及失败处理统一遵守[执行规范](../references/standards/execution.md)。


### 风险与场景对应检查

风险标识保持唯一；需要可检查的场景引用时，矩阵使用 `场景:标识`，在行为与异常场景正文用 `### 场景:标识` 定义。自然语言场景必须能对应到具体正文；无法核对定义或覆盖时明确标为待人工核对。

显式引用和定义都检查完整标识，使用字母、数字、点、下划线或连字符；多个引用以空格、顿号、逗号或分号分隔，可用反引号包裹。非法、空或悬空引用报错，不按有效前缀判为通过；非法场景定义同样报错。

```bash
python3 -B <SWE目录>/scripts/check_artifacts.py --kind test --file <测试设计路径>
```

脚本执行本模块产物格式校验、重复风险或场景标识、悬空场景引用检查；风险是否充分、预期是否正确和替身能证明什么仍需内容审查。完成内容调整后重跑。

## 资源

| 资源 | 用途与条件 |
|---|---|
| 用户目标、共同约定、任务范围与验收要求 | 决定本轮应交付或审查的内容，不替代专业依据 |
| 业务模型、系统设计、接口协议、适用交互规范、已确认需求及历史风险 | 按下方输入规则定位权威位置和条件性依据，缺少关键内容时停止依赖它的操作 |

输入按用户路径、项目索引和实际引用定位，只读取当前相关部分。资源不足明确影响；未确认的业务规则不由实现、测试或界面补造。

### 输入与现状

读取已确认需求、业务模型、系统设计、协议、适用交互规范和变更范围。现有测试是实现证据，不自动成为正确需求。输入类型和格式统一引用共同 schema；业务语义按当前相关模型审查。


## 路径

### 执行前范围核对

先确认任务、权威输入和实际可写文件，在首次写入前固定范围：

```bash
python3 -B <SWE目录>/scripts/check_scope.py snapshot --root <目标Git根目录> --baseline <项目外全新临时文件> --allow-file <允许文件相对路径>
```

多个文件重复 `--allow-file`；只有明确职责独立的目录才可用 `--allow-dir`。运行产物也要事先限定；混合源码目录和整个仓库不能当作可写范围。默认只维护自己负责的产物，不因为检查失败修正其他模块产物。

### 执行前文档检查

业务模型及其他文档格式统一由[共同产物规范](../references/standards/artifacts.md)维护。按声明的输入类型使用共享校验器，仅读取相关专业依据，不要求加载生产方工作流。

缺失或不合格的必需文档仍阻止执行。

必需输入：当前验证对象及其已确认要求。业务规则读取业务模型，模块边界读取系统设计，接口行为读取协议，UI 行为读取交互规范；仅加载本次场景依赖的类型。创建测试设计无需已有该文档；修改时先校验现有文件。

查找权威文档，依据业务规则和公共协议确定预期行为；读取已有实现只用于确定接入方式和历史风险，不用当前代码输出反向生成预期。必需文档缺失、格式不合格或不足以支持当前范围时停止。不编写测试代码或变更执行配置。

先按用户给定路径、项目文档索引和相关引用定位文件，再按对应类型运行格式校验。多个候选来源无法确认权威位置时停止并说明，不任意选取。已通过格式检查仍需核对当前范围和关键语义；存在阻断项时不开始本 Skill 的实际执行。

使用本 Skill 的实际安装路径执行以下命令，条件性文档仅在上述条件成立时检查，`<文档路径>` 替换为实际文件：

```bash
python3 -B <SWE目录>/scripts/validate_documents.py --kind business-model --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind system-design --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interface-protocol --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interaction-standards --file <文档路径>
```

缺失和不合格的输入只作为阻塞反馈；本 Skill 不修复职责外输入或调用其他 Skill 越界修改，需要纠正时先结束当前环节，再进入对应 Skill。所需输入已存在且合格时直接执行当前任务，不额外请求确认。

### 测试设计

1. 从用户路径、状态转换、公共协议和历史失败提取重要风险。
2. 为每个风险确定场景、前置条件、输入、操作、预期结果与禁止发生的副作用。
3. 选择能够证明该风险的层级：静态检查、单元、模块协作、集成、HTTP、浏览器、目标平台或真实外部服务。
4. 明确替身边界、数据隔离、运行环境、观察方式与不可证明的部分。
5. 高风险重构先冻结外部行为基线；异步协作优先构造请求顺序、身份变化、版本变化和生命周期场景。

不要求每个任务覆盖所有层级。可逆、低影响变化优先使用已有检查和直接验证；新增测试应保护有价值的行为。

### 设计完成标准

在文档中明确风险、场景、前置条件、输入、操作、预期结果及禁止副作用；定义替身边界、数据隔离、执行方法、证据、清理及停止条件。仅制定设计不要求实现可运行，也不执行会改代码或数据的验证。

设计应足以指导测试实施；不能用当前实现结果反向定义正确答案。交付格式合格的测试设计及必要说明，测试代码由 swe-testing-impl 实施，实际证据由后续验证取得。

### 产物契约与格式校验

唯一文件产物是测试设计文档。说明写入回复，不生成测试代码、执行报告或其他文档。

- `test-design`：测试设计，默认位置 `design/test-design/test-design.md`；使用 [模板](assets/test-design.md)。

遵守[本 Skill 文档规则](references/document-format.md)和[本 Skill 的机器契约](references/artifact-contract.json)。实际文档必须有完整必需章节，表格字段和判定值必须符合契约；模板占位符必须替换，不适用项写明原因。

校验命令使用本 Skill 的实际安装路径执行，`--file` 可以指向任意目标项目，工具不绑定项目路径：

```bash
python3 -B <SWE目录>/scripts/validate_documents.py --kind test-design --file <文档路径>
```

交付前校验本 Skill 负责的设计产物并修正其格式错误；其他文档只读校验，缺口反馈归属，不跨范围修改。每次实际修改与执行记录在回复或已有任务记录中说明，长期设计不维护任务进度。文档校验通过只证明约定格式与局部引用成立，不证明业务、设计或运行行为正确；继续执行该 Skill 的语义检查和对应验证。

### 产物对应关系检查

交付前必须执行“规则”中对应关系检查的命令，核对 `errors`、`checked` 和 `unverified`。发现错误时修正本模块产物并重跑；对未自动检查的自然语言关系逐项人工核对，不能把脚本退出码 0 当作全部内容通过。

### 结束核对与覆盖确认

```bash
python3 -B <SWE目录>/scripts/check_scope.py check --root <原Git根目录> --baseline <原临时基线文件>
```

格式或本模块产物错误在允许范围内修正后，重新执行相关检查和范围核对；内容审查产生新改动时同样重查。上游缺口、越界、生产缺陷或环境阻塞按职责反馈，不以弱化检查取得通过。

每项本轮目标对应产物和检查结果，必要能力未验证时明确限制，不能把“代码或文档已写完”当作已验收。修改范围核对还需人工确认允许文件内的职责与共用配置条目。

收尾前确认结果与实际证据一致，简述检查、未覆盖项和阻塞，不默认生成报告。提交、推送或对外回写遵循用户授权。
