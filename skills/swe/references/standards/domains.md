# 领域能力与改动边界

五个领域是能力，不是流水线。任务可使用一个领域或在明确授权下切换领域；既有产物可直接作为依据，不要求依次执行全部能力。[adoption](../../adoption/SKILL.md)组织接入、更新和退出，按需使用领域能力，不改变产物所有权；本轮不提供 Bug 修复、需求开发等任务流程，也不自动创建任务或派发 Agent。

## 产物所有权

| 领域 | 可维护的产物 | 只读边界 |
| --- | --- | --- |
| 业务模型 | 实体、行为、流程、业务规则的权威模型 | 架构、生产代码、测试、部署 |
| 系统设计 | 架构 YAML、结构设计、独立数据契约、技术与运行约束、生成视图 | 业务模型、生产代码、测试、实际部署配置 |
| 代码实现 | 指定模块生产代码、生产依赖、必要实现配置、程序内部对象组装 | 业务模型、架构、独立契约、所有测试产物、部署配置 |
| 测试 | 测试设计、单元／集成／端到端测试、替身、夹具、快照、测试配置 | 业务与架构预期、独立契约、生产代码、部署配置 |
| 发布交付 | 发布构建、CI/CD 发布部分、部署与环境配置、制品清单、发布和恢复资料 | 业务与架构、生产代码、测试及测试阈值 |

独立权威契约可以是 Markdown、OpenAPI、Protobuf 或源码类型文件；按其权威职责判定，不按扩展名判定。生产依赖属于代码实现，测试依赖属于测试，发布工具依赖属于部署。共享包清单、配置或流水线按条目划分，不因修改一项就取得整个文件所有权。

测试文件可以位于模块目录内。代码实现必须排除测试、夹具及快照，测试必须排除生产文件。混合目录使用准确文件清单建立范围基线，不能授权整个模块目录。文件级检查无法证明共享文件的条目边界，必须人工核对差异。

## 每次调用的范围

开始前明确当前领域、目标产物、权威依据、可写文件或条目、运行产物与完成证据。允许范围是用户授权与领域职责的交集；领域能力本身不授予修改整个仓库或外部系统的权限。

发现其他领域问题时说明依据、影响和归属，不顺手改写。若原任务已明确授权跨领域工作，可显式切换能力并为下一范围建立独立检查；不得扩大原基线掩盖先前越界。缺少依据只阻塞依赖它的工作。标准、Schema 和 CLI 属于共享能力维护，仅在明确维护任务中修改。

## 自检与只读审查

每个领域在自己的范围内完成工作、自检、修正和交付。CLI 负责已编码规则，Agent 判断专业语义，项目工具提供行为与运行证据；没有单独的 Check 领域。

用户只要求审查时采用只读模式，使用共享执行规范的指纹核对，不修改本领域或其他领域产物。只读模式不运行写缓存、日志、报告或业务数据的命令；不能以临时副本规避。需要动态验证时说明缺口，按既有授权另行进入允许写入的测试或部署模式。

代码实现可以运行已有测试，部署可以调用已有验收入口，但都不能更改断言、快照、测试数据或测试配置。运行产物与副作用须预先限定；执行测试与维护测试是不同权限。
