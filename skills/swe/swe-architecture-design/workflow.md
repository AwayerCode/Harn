# 系统架构设计

## 目标

交付与业务目标一致的分层、依赖方向、运行组装、技术选型和跨层约束。模块与协议细节由模块设计承接。

## 规则

遵守[按需加载与职责边界](../references/standards/loading.md)，按当前对象读取共同标准与项目契约；不加载其他专业工作流来完成本职责。

阅读[专业方法](references/professional-method.md)。只维护系统设计中的设计依据与范围、责任分层、横切基础设施与运行组装、技术选型，以及本范围的文档信息和待确认问题；模块表、状态所有权、协作路径和代码映射由模块设计维护。两者可共用现有系统设计文件，但本次可写章节需明确，交付前人工逐节核对。

不预设无业务依据的空层或固定技术栈，不修改业务模型、协议、实现和测试。模块划分尚未完成时明确为架构局部产物，不宣称整套设计已可实施。

共同要求引用[工程标准](../references/standards/engineering.md)、[执行规范](../references/standards/execution.md)及[产物规范](../references/standards/artifacts.md)。只加载本任务适用部分，不复制或自行改写标准。

## 资源

必需：任务、业务依据、项目约定和运行约束。按需：现有系统设计、目标技术官方资料。文档沿用项目位置；新建使用[架构局部模板](assets/architecture-design.md)；模块设计随后在同一权威文档中补齐其他章节，完整结构参照[系统设计模板](assets/system-design.md)。不为填满模板编造职责外设计。

## 路径

1. 确认目标与本次可写文件、章节，按执行规范建立项目外范围基线。
2. 从业务职责形成相关层次，说明运行协作、代码依赖方向与抽象边界。
3. 确定运行组装和关键技术，查证影响决策的外部能力，区分确认与建议。
4. 运行局部校验，仅验证架构负责章节；补做架构语义和改动章节审查，运行范围检查。局部通过不表示整份设计已可实施。

5. 将模块责任、接口和质量要求的待设计项交给模块设计，不直接补写其内容。

局部检查命令：

```bash
<SWE目录>/bin/swe-cli documents --root <项目根目录> --kind system-design --profile architecture --file <系统设计路径>
```

检查失败只修正本职责产物；依据不足或涉及契约变更时反馈对应责任方。交付实际改动、检查证据、未验证项和阻塞；提交、推送、发布另循用户授权。
