# 结构审查方法

以项目权威系统设计和共同约定为准，不将当前目录反向解释为正确设计，也不凭通用模板判错。模块是否应存在取决于当前设计及实施阶段；尚未实施的计划位置缺失只能说明现状，不能直接认定违规。

设计表达与检查选择遵循[共享 CLI 约定](../../references/cli.md)。存在多个冲突来源时停止依赖它的检查；依据缺失或不能支持当前对象时记录缺口，无关缺口不阻止其他明确部分。

| 检查对象 | 必须核对的内容与证据 |
|---|---|
| 目录、模块和文件归属 | 设计责任与实际位置是否对应，是否存在缺失、重复、废弃、错误归属或未约定结构 |
| 公开入口 | 入口文件是否存在，实际导出是否兑现公开能力，消费者是否绕过入口访问内部文件 |
| 文件依赖 | 静态导入、导出、类型引用及明确动态引用是否遵守设计方向、抽象边界和模块独立性 |
| 文档、配置与接入 | 权威来源是否唯一，配置是否跟随消费者，路由、资源、别名和生成入口是否引用实际文件 |
| 测试与校验接入 | 已约定入口的位置与引用是否成立，不分析测试断言或运行效果 |

读取导入、导出和注册声明以确认文件关系，不沿调用链判断业务逻辑。项目自带检查器先核对命令及脚本的副作用；没有可用只读检查器时，用文件清单、路径解析和源码声明逐项人工核对，不静默略过依赖检查。语言、别名、代码生成或动态关系无法解析时标为未验证，不用简单文本匹配冒充确定的依赖结论。
