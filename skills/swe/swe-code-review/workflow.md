# 代码审查

## 目标

交付有可达触发条件、准确位置、证据和影响分级的代码问题，以及已审查风险和未验证范围。

审查的完成是覆盖与证据说明完整，违规也可交付；不要求修复所有问题。

## 规则

涉及模块、异步、状态或资源生命周期时，读取[实现与运行约束](../references/standards/implementation.md)的适用章节。

遵守[按需加载与职责边界](../references/standards/loading.md)，按当前对象读取共同标准与项目契约；不加载其他专业工作流来完成本职责。

### 文件写入边界（强制）

本 Skill 只做 Review，禁止新增、修改、删除、移动或重命名任何文件，包括设计、源码、测试、配置、快照、报告、日志与缓存。只能读取已有产物并在回复中交付结论，不自动修正，也不在 Review 中调用其他 Skill 执行修改。

检查命令必须确定无文件写入、副作用或自动修复。文档校验使用 Python `-B` 禁用字节码缓存；测试、构建、格式化和代码生成若会写文件就不得执行，说明未执行及原因。不能通过先写后删除、临时副本或事后恢复绕过只读边界。

发现问题时仅说明证据、位置、影响与建议归属。即使任务同时要求修复，也先完成并结束 Review，再切换到相应 Design 或 Implementation Skill；该 Skill 自行检查输入和写入范围，Review 不承担修复。

### 职责与判定要求

判断代码是否实现预期行为、保持必要约束，并找出值得修正的具体问题。适用于任意项目与技术栈，不预设固定架构。

先确认审查对象、比较基线和任务要求：工作区改动、特定提交、分支、Pull Request 或指定模块。范围可从当前上下文可靠推断时直接开始；无法确定且影响结论时明确询问，不自行选择无关基线。

### 依据与检查范围

必需输入是审查对象、适用任务要求及变更审查的比较基线。按每项检查判断是否需要补充文档，不将全部设计文档齐备作为开始代码审查的门槛。

| 检查内容 | 所需依据 |
|---|---|
| 能由代码、实际调用路径、语言或库的明确规则确认的错误 | 相关代码及适用规则；例如可达的越界访问、空值解引用或无释放路径，不强制要求设计文档 |
| 模块责任、允许依赖及架构是否符合设计 | 对应权威系统设计 |
| 公共能力、调用语义及兼容承诺是否兑现 | 对应权威接口协议 |
| 业务规则、UI 约定或测试设计是否兑现 | 对应业务模型、交互规范或测试设计 |

需要的依据缺失、格式不合格、冲突或不支持当前结论时，只停止依赖它的检查，继续有独立依据的部分。记录未检查对象、缺失依据及其影响，不从现有实现反推正确业务或设计，不把部分审查报告成全部通过。审查对象本身不可取得，或所有适用检查均无充分依据时，交付阻塞说明。

### 审查重点

按当前变化选用，不把每项都作为必做清单：

- **业务正确性**：输入、条件、计算、顺序、状态变化与副作用是否符合需求；是否以空值、假成功或默认值掩盖失败。
- **模块与协议**：职责、状态归属、公共入口及依赖是否符合项目设计；调用者与提供方的类型和执行语义是否一致。
- **异步与资源**：迟到结果、身份或上下文切换、版本确认、并发冲突、重试、取消和释放是否正确；是否重复执行或覆盖新修改。
- **数据与权限**：授权是否在实际业务边界执行；事务、迁移、持久化与恢复是否保护一致性；敏感信息是否进入不应进入的输出或日志。
- **兼容与接入**：真实调用者、生成产物、配置、路由、构建、静态资源与部署引用是否同步，旧入口是否仍被使用。
- **用户交互**：可见状态与实际结果是否一致；操作、导航、未保存内容及失败恢复是否遵守业务能力和交互约定。
- **测试证据**：是否验证结果及禁止发生的副作用；是否只验证实现结构；测试范围能否证明所声称的能力。
- **性能与维护**：是否存在可说明的重复工作、无界增长、查询放大或资源泄漏；复杂性是否造成具体理解、修改或运行风险。

性能与安全问题需要结合可达路径、输入条件和实际影响，不凭关键词或假想场景下结论。格式、命名和个人架构偏好不作为缺陷，除非违反明确约定或造成具体问题。

### 问题成立的标准

正式问题应具备可达的触发条件、明确影响，以及代码、契约或运行结果支持。合理的静态推导可以作为证据，不要求所有问题都实际复现；清楚区分静态确认与运行验证。

变更引入的问题定位到最小相关改动；完整上下文用于解释影响。不要因为代码看起来可疑就断定有错，不重复报告已被实际防护排除的问题。

信息不足的疑点列为待确认问题，说明缺失依据；不伪装成确定缺陷。缺少测试本身不自动构成产品错误，但可以单独指出具体风险尚缺验证。

### 优先级

- **P0**：需立即处理的严重问题，例如已确认的大范围数据破坏或系统失效；保留给证据充分、影响明确的情形。
- **P1**：应在交付前处理的高影响问题，例如关键路径不可用、权限突破、数据丢失或重复执行重大副作用。
- **P2**：应修正的常规缺陷，在具体条件下产生错误行为或明显维护风险。
- **P3**：影响较低、可择期处理的具体问题。

优先级依据影响、发生条件与紧迫性，不能只依据修改难度。项目已有分级时沿用项目定义。

### 只读结果核对

执行前取得共享脚本的文件指纹并保存在执行上下文，不生成基线文件。结束或因输入缺口提前退出前，比较原指纹。发生变化时停止后续检查，报告变化与归因未确认，不自动回退或重新记录基线。无 Git 环境或无法取得指纹时明确只读核对未验证，仍可做有依据的静态审查。

### 检查要求与执行

问题需有明确影响及证据；静态推导与运行验证区分。记录每项适用风险的审查结果，不以没有报错替代覆盖确认。

| 检查执行 | 作用与条件 |
|---|---|
| [本模块格式规则](references/document-format.md)与 [validate_documents.py](../scripts/validate_documents.py) | 检查必要输入及本模块设计产物的格式和引用；不证明专业内容或运行行为正确 |
| [check_scope.py](../scripts/check_scope.py) | 核对实际写入范围或只读结果；Python 3 标准库和 Git，属于规则的检查执行，不是业务资源 |
| 内容审查、项目检查与实际验证 | 按下面保留的专业要求和完成标准确认内容与行为；涉及运行先确认工具、环境、权限、输出位置和副作用 |

检查执行、范围覆盖、退出码及失败处理统一遵守[执行规范](../references/standards/execution.md)。


## 资源

| 资源 | 用途与条件 |
|---|---|
| 用户目标、共同约定、任务范围与验收要求 | 决定本轮应交付或审查的内容，不替代专业依据 |
| 审查对象及比较基线、设计与协议、相关业务或交互依据、调用路径、已有测试和运行证据 | 按下方输入规则定位权威位置和条件性依据，缺少关键内容时停止依赖它的操作 |
| 已有项目工具、环境及历史证据 | 按当前风险选择实际检查；历史通过不代表当前通过，副作用或环境不明时先核实 |

输入按用户路径、项目索引和实际引用定位，只读取当前相关部分。资源不足明确影响；未确认的业务规则不由实现、测试或界面补造。

### 输入与现状

读取适用的工程约定、需求、设计、协议、改动和相关测试。变更审查区分新增问题与既有缺陷；既有代码审查按用户指定范围报告。审查深度与变化规模及风险相称，不默认扩展成全仓审计。


## 路径

### 执行前范围核对

先确认对象、比较基线、实施阶段与适用风险，然后在其他检查前记录只读指纹：

```bash
python3 -B <SWE目录>/scripts/check_scope.py readonly --root <目标Git根目录>
```

将输出 `sha256` 保存在执行上下文；后续输入检查失败也必须在交付前完成结束核对。

### 执行前文档检查

业务模型及其他文档格式统一由[共同产物规范](../references/standards/artifacts.md)维护。按声明的输入类型使用共享校验器，仅读取相关专业依据，不要求加载生产方工作流。

先取得审查对象及适用要求，变更审查还需明确比较基线。按“依据与检查范围”逐项确定所需文档，只定位和校验当前检查实际依赖的类型。

按用户路径、项目文档索引和实际引用查找权威文档。多个候选来源无法确认权威位置时停止依赖它的检查并说明，不任意选取。格式通过仍需核对当前范围和关键语义。

将审查项分为依据充分、依据缺失或冲突两类；立即执行依据充分的检查，其余记录阻塞及影响。缺少设计不能作为代码正确的证据；已有代码也不能替代应由设计定义的业务或架构要求。不自动补建上游文档。

使用本 Skill 的实际安装路径执行以下命令，条件性文档仅在上述条件成立时检查，`<文档路径>` 替换为实际文件：

```bash
python3 -B <SWE目录>/scripts/validate_documents.py --kind system-design --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interface-protocol --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind business-model --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind interaction-standards --file <文档路径>
python3 -B <SWE目录>/scripts/validate_documents.py --kind test-design --file <文档路径>
```

文档缺口只阻塞依赖它的检查；本 Skill 不修复输入或调用其他 Skill 越界修改。完成有依据部分并交付缺口后结束 Review，再由对应 Skill 纠正。所需依据充分时直接执行，不额外请求确认。

审查单位是代码路径与可达行为。文件位置只用于定位问题，不重复以目录整理为目标的结构检查；测试仅用于确认当前代码风险，不承担完整测试设计审查。

### 工作方法

1. 明确此次变化的目标、允许改变的行为及必须保持的行为，检查改动清单与实际范围。
2. 从用户入口或公共能力追踪调用者、实现、依赖、数据与副作用，读取必要上下文，不只看 diff 局部。
3. 比较改动前后行为，重点检查关键路径、错误路径、异步时序、权限边界及兼容性。
4. 核对测试是否保护实际风险，检查替身、断言和基线是否掩盖缺陷。必要时运行针对性的已有检查或最小复现。
5. 对候选问题确认触发条件、受影响行为、代码位置与证据，检查是否已有防护或被上游约束排除。
6. 合并同一根因的问题，按影响与紧迫性排序，交付审查结论、实际验证与未覆盖范围。

只审查，不修改任何文件，不补造上游文档，不在审查中调用修正。需要修复时仅说明归属，结束 Review 后由独立 Design 或 Implementation 执行。

### 交付格式与完成标准

结果先列问题，每项包含：

- 优先级与简短标题。
- 准确文件位置及尽量小的相关行范围。
- 触发条件、错误行为与影响。
- 必要证据和修正方向；不要求给出整套实现方案。

随后简要说明实际验证、未覆盖范围和待确认问题。遵守当前平台或项目要求的审查格式；无确定问题时直接说明，并保留必要的验证限制，不为凑数量制造问题。

完成时检查：范围与基线明确；重要路径及风险经过审查；每个问题有证据且可操作；优先级合理；没有把历史测试通过当成当前验证，也没有宣称静态审查能证明全部运行行为。

### 产物约定

审查结论直接在回复中交付，不生成独立执行报告。沿用本 Skill 的问题证据、位置、影响分级与覆盖边界要求；不在 Review 中提交、推送、部署或回写任务及 Pull Request；结论直接回复。

### 结束核对与覆盖确认

```bash
python3 -B <SWE目录>/scripts/check_scope.py readonly --root <原Git根目录> --expected <原sha256>
```

逐项核对本轮适用对象和风险：已检查项有依据及证据，待确认项有缺失信息，未检查项有原因。不适用有明确理由。审查发现问题无需修复或重跑到全绿；运行失败只说明相应验证状态，不能直接当成产品缺陷。结论限于实际覆盖，不能据此宣布产品整体完成。

收尾前确认结果与实际证据一致，简述检查、未覆盖项和阻塞，不默认生成报告。提交、推送或对外回写遵循用户授权。
