# 更新与退出

## 更新

更新整个 SWE 包，adoption 和五个领域不独立安装或版本化。按 [CLI 安装与版本约定](../../references/cli.md#安装与版本)使用匹配平台与绑定的工具，不维护第二套 CLI、Schema 或运行规则。下述项目外副本仅用于本次换版、恢复及最终验证，完成后清理。

1. 记录现有包来源与版本、CLI 版本、设计检查结果、项目指引和接线条目，识别本地修改。既有任务先用原工具完成原基线检查；本次更新另建固定范围基线，不重建基线掩盖差异。
2. 在项目外保留原包的完整副本，包含 `bin/`、`runtime.json` 和 Skill 文本，并验证副本的版本、摘要和可执行性。用这个原版本副本建立本次基线并执行更新后的 `scope check`，避免替换包时失去原工具。临时目录须在宿主允许范围内，不作为另一套长期安装。
3. harn 没有 `update` 命令，`install` 遇到已有目标目录会拒绝覆盖。先在独立临时项目安装明确版本和平台的完整包：在该临时项目目录执行 `harn install --source <完整平台包URL> --version tag:<版本> --path skills/swe`，产物位于其 `.agents/skills/swe/`。不在当前项目反复执行 install，不先删现有包腾位置。
4. 比较新旧包，保留项目自有内容并明确本地修改如何迁移。核对候选包的完整性、`runtime.json` 绑定及 CLI 版本，再显式替换正式 SWE 目录。此处验证的是工具包，不是候选 YAML 设计预演。不能只覆盖新增文件留下已删除的旧入口，也不能把旧绑定配给新二进制。新包不完整、绑定错误或本地修改尚未处理时不替换。
5. 用新包执行首次接入的发现、单独及批量设计检查；用保留的原版本工具完成原基线的范围检查。对新增诊断区分规则变化、原有缺陷和迁移问题；YAML 由系统设计能力维护，不能因升级放宽约束。接线只改对应条目，测试和发布语义仍归对应领域。
6. 更新记录及结果后执行最终范围检查，成功后清理本次临时副本。失败时明确未完成状态并保留恢复依据；如需恢复，仅恢复可确认属于本次更新的内容，不覆盖随后产生的用户修改。

## 退出

移除 Skill 只在没有其他接线与消费者时足够。先依据接入记录与当前文件检查真实使用者，不能只凭旧清单批量删除：

1. 明确退出范围，检查其他应用是否共享 SWE 包。在项目外保留当前完整包并核验 CLI 版本、摘要和可执行性，用其建立退出基线并保留到全部验证完成。退出记录和可清理配置也须纳入范围；不要删除正式包后才寻找验证工具。
2. 移除本次接入维护的 Hook、CI 或脚本中的 SWE 调用和 Agent 指引引用；共享文件逐条处理，保留其他检查、发布逻辑及用户修改。恢复旧值前核对当前值仍属于本次接线；无法确认的条目列为待处理。
3. 默认保留项目 YAML、业务模型、代码、测试、部署资料和人工维护文档。生成 HTML 是否清理依照产物用途和任务范围；保留时说明它是历史视图。若用户另行要求删除 YAML，由系统设计领域处理，先评估父级重新接管范围；删除后用保留工具重新发现并检查剩余作用域。没有剩余 YAML 时记录“无设计”，不能把 CLI 返回 2 当成通过。
4. 确认当前项目和其他共享使用者不再引用正式 SWE 包，才移除其安装目录及仅供它使用的忽略条目。只退出某个子项目时，其他应用仍使用的包必须保留。harn 没有卸载状态或自动恢复数据库，不调用不存在的卸载命令，也不删除其他 Skill。
5. 检查已知配置中是否残留失效调用，运行受影响且获授权的项目检查，更新接入记录中的退出状态与保留项。最后用项目外保留的原版本 CLI 执行原基线 `scope check`；失败则报告并保留验证工具，不扩大基线或回滚用户修改。
6. 全部必要验证完成后清理临时工具副本。项目外清理不属于 Git 范围检查覆盖对象，须单独确认仅删除本次临时目录。退出不改写 Git 历史，不回滚整个共享配置文件。
