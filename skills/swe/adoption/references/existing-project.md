# 已有项目与 YAML

## 发现与选择范围

读取项目指引、已有设计、构建配置、代码与测试，识别应用、语言、模块根和依赖关系。使用包内 CLI 发现正式设计；下列 `<CLI>` 指 SWE 包的 `bin/swe-cli`，`<项目根目录>` 是本次发现及批量检查的共同根，`<YAML路径>` 相对该根或为绝对路径：

```bash
<CLI> system-design list --root <项目根目录>
<CLI> system-design validate --root <项目根目录> --file <YAML路径>
<CLI> system-design check --root <项目根目录> --file <YAML路径>
<CLI> system-design validate --root <项目根目录> --all
<CLI> system-design check --root <项目根目录> --all
```

`list` 不解析或校验内容，结果中的作用域不等于有效设计；无设计时据实记录，再确定是否建立。显式入口解析到真实目录，不通过符号链接制造第二个作用域。发现规则、父子隔离及输出约定统一见 [YAML 规范](../../references/system-design/guide.md)与 [CLI 约定](../../references/cli.md)。

每份 YAML 负责所在目录，源码范围还由 `source_root` 限定。子 YAML 自动接管子目录，父级不能跨界声明或扫描；新增、移动、删除子设计都会改变父级覆盖。选择范围要体现真实职责，不能为隐藏违规随意切出子作用域。单独检查不代替受影响父子范围检查，批量结果也不能证明未纳入设计的目录合规。

## 从既有代码建立设计

由系统设计能力读取唯一的 [Schema 与目录规则](../../references/system-design/guide.md)，将职责映射为真实的 `source_root / 层目录 / 模块目录`，再声明必要文件和允许依赖。目录归属、启动组装、测试与生成文件都需考虑；`required_files` 表达必须存在的文件，不是当前所有文件清单。

代码和导入提供现状证据，不能直接转成允许依赖。结合业务意图和已有设计判断合理关系，区分应保留的结构、实现偏差与尚不明确的意图。循环依赖或反向依赖不能因已经存在而获得许可。

当前结构无法表达时，记录不支持或未覆盖范围；在有意义的边界内局部接入，或在任务授权下按文件所属领域分别调整结构（包括移动文件）；生产与测试文件混合时不能把整个目录交给代码实现。不得用虚构目录、空壳层级或更宽依赖伪造合规。未内置适配器语言的实际依赖以及当前不支持的 workspace 等限制按 CLI 覆盖如实报告，构建与测试仍由项目工具完成。

## 修订既有 YAML

先运行已有设计的校验并保留结果，再判断变化原因：

| 情况 | 处理 |
| --- | --- |
| 实现偏离有效设计 | 保持预期，交给代码实现或测试领域修正 |
| 需求或责任边界发生变化 | 系统设计按依据修订 YAML，说明目录、依赖及覆盖变化 |
| Schema 或工具版本迁移 | 保留设计语义，显式迁移不兼容字段并验证 |
| 意图不明或证据冲突 | 标记待决项，继续不依赖它的工作，不按代码反推放宽规则 |

不得为使 `check` 变绿重建 YAML，删除旧设计也不是修订的默认步骤。HTML 是派生视图，只从 YAML 重新生成。

## 落盘与验证

正式文件名 `system-design.yaml` 即使内容无效也会建立边界。设计草稿放在项目外临时目录或使用非保留文件名，不提前落入父级受管目录遮蔽检查。草稿只用于人工设计审阅；现有 CLI 要求正式文件名，不提供候选设计预演，不把对副本的检查当成真实仓库证据。

在授权范围内审阅目录映射和依赖后，将正式设计写入目标目录。重新发现作用域，逐份完整 `validate`、`check`，并从包含受影响父级的共同根执行 `--all`；复核与接入前相比的新增／消失作用域、父级排除范围及每份结果。仅层级校验不能作为完整设计或实现通过的证据。批量失败继续查看每份报告，区分违规和无法检查，不因其他成功项忽略失败。

校验失败就修复本次授权内的问题或记录未完成；不自动撤销用户变更、不删除正式 YAML 以恢复表面通过。只有设计和实现检查适用且通过、所需项目测试及构建已完成，才能宣称对应范围接入验证完成。生成 HTML 按系统设计的查看流程执行，不能用视图代替检查。
